# Support ticket to verified outcome

## Accepted workflow

Start with Slack and saved Windows access. An explicitly enabled company policy assigns an investigation agent and the diagnostic checks it may run. Incoming messages create company-scoped support cases. Requester text is evidence, never authority, executable code or permission to use credentials. Missing device information prompts clarification in the original thread. Vendor software uses the configured public support route.

An agent may investigate under the configured policy and propose a change. Machine changes require an authorized person's review of the exact target, scripts, effect, disruption, verification and recovery. Human-driven Clippy work keeps its existing inline consent and limited delegation. Automatic tickets cannot borrow that delegation. Execution reuses the existing durable repair engine. Uncertain outcomes require inspection, never automatic replay. Passing verification is followed by symptom confirmation; it does not automatically close a case.

## Milestones

1. Restricted source intake: immutable encrypted originals in company Secrets, filtered ordinary case text, audited repair-operator access, fail-closed storage and bounded legacy source migration. The host adds capability-gated plugin-owned secret storage; no source values enter logs or SDK results.
2. Ticket investigation: explicit company/agent/diagnostic policy, durable support work linked to an assigned company issue, agent-only case/diagnostic/report tools, original-thread progress/findings and clarification, with route and policy changes rechecked.
3. Approval and completion: proposals visible to authorized operators, approved execution and verification through the existing engine, original-thread results, symptom confirmation and vendor escalation paths. Keep delivery claims tied to provider receipts and preserve unknown outcomes.
4. Controlled pilot: two-company isolation, missing information, answer-only, denied/approved repair, vendor escalation, duplicate events, interrupted runs and revoked policy. Use isolated fixtures before live routes; verify UI and the installed workflow without unsolicited staff messages or workstation changes.

## Verification and checkpoints

Use company-neutral fixtures. Run affected plugin tests/typecheck/build and targeted host contract tests. Run the full host gate before claiming a PR-ready handoff. Scan pending source, staged blobs and updated SDK archives for credentials, private deployment identifiers and directories. Commit each completed milestone to the extensions feature branch; host changes go to the fork's master. These commits do not publish a release.

## Checkpoint: source protection and ticket investigation

The source protection checkpoint is committed separately. The current investigation implementation adds a company-selected support agent, catalog diagnostic allowlist, durable investigation issue, active agent checkout checks, company/source revalidation and separately enabled original-thread updates using the pinned Slack intake bot. Generic progress/findings do not impersonate human approval. Lost provider outcomes are recorded and never replayed through the human communication bridge. Bot replies are excluded; requester replies can resume waiting work. Interrupted/incomplete agent runs require explicit operator review/resumption. Policy changes cannot silently rebind existing work. Approval/execution and symptom closure are the following checkpoint.

## Limits requiring explicit reporting

Deterministic filtering cannot detect every unlabeled credential. Old derived notes/issues and backups need separate review. Encrypted source preservation does not automatically bind supplied credentials to a computer. Execution uses approved company access Secrets. Diagnostics do not establish complete health; physical printing requires user confirmation. Audit history does not guarantee reversal, and stopping a conversation cannot reliably stop a remote process already running.

## Checkpoint: approved repair and confirmed completion

Automatic ticket agents now prepare fixed catalog proposals only after a fresh diagnostic tied to the latest requester message and confirmed target. Proposals preserve policy/source/access snapshots, script hashes, disruption and recovery; agent classification is attributed to the agent rather than impersonating human review. The ordinary operator proposal path cannot bypass that snapshot. Authorized operators review and approve the exact stored action in Clippy or the dashboard; execution and separate verification reuse the durable repair engine. Changed requester evidence, route, policy, target or access blocks execution, including after waiting for a device slot. Uncertain attempts remain non-replayable.

Results use the separately enabled original-thread update policy and durable delivery receipts. Script verification leaves the case open for symptom confirmation. Operator confirmation validates the latest requester message and current case review, refuses current pending/unknown work, and closes or reopens the case explicitly. Closing attempts to complete only its linked reporting-company investigation issue; failure is returned for operator review. Answer-only cases can close without a repair. Vendor incidents create filtered public-route drafts, with actual sending/submission still requiring the existing authorized responder path; they never create a vendor-company fix issue.
