## Technical approach

- Keep React, the existing router, company context, query layer, providers, and plugin contribution system. Prefer wrapping/reorganizing real components over rewriting workflows.
- Define one host-owned workspace/navigation description for core and plugin surfaces: stable workspace identity, label, scope kind, route resolver, availability, local navigation, pin/search metadata, and capability restrictions. Confirm its fit with current plugin slots before finalizing interfaces.
- Treat workspace, company scope, selected record, and pane state as separate concerns. Do not infer one from a remembered URL string alone.
- Preserve old route entry points through compatible routes/redirects. Route normalization must support plugin slugs, query strings, hashes, global pages, and legacy links without double prefixes.
- Clear or scope cached/selected data during company changes; late responses must not repaint a previous company's content. Keep unsaved drafts explicitly bound to their original company/conversation.
- Prefer reversible shell adoption. Choose a narrowly scoped fallback/toggle or staged route integration in P0/P1; document how to return to the prior UI without reverting user data. A parallel domain implementation is not the fallback strategy.
- Do not alter API/domain names merely to change user-facing labels. When real contract changes are needed, synchronize db/shared/server/UI and audit/authorization behavior.
- Keep extension repositories and installed plugin builds explicit. Do not modify a cached/generated plugin copy and assume the source or running install changed.

**Result: 15 real, confirmed findings, all fixed the same session — full detail and outcomes in the review tool's own findings report, not duplicated here. The two most serious, in order of severity:**

1. **`ui/src/components/SidebarNavItem.tsx`'s peek-mode click handler navigated in the wrong company.** `setSelectedCompanyId(peekedCompanyId, ...)` only queues a state update; the very next line's `navigate(to)` still resolved its company prefix from the *current* page's URL, not the peeked company, because there is no synchronous link between the two. A hover-flyout click could silently open the current company's own page instead of switching — with a normal, valid, single-prefixed resulting URL, so it didn't look broken. **This coexisted with the B01 fix Barry confirmed live** — his test (collapse sidebar, hover a different company, click Clippy, check the address bar has no double prefix) was specifically about the double-prefix symptom and passed correctly for that; it wasn't positioned to catch "navigated within the wrong company to a page that still looks completely normal." Fixed by resolving the peeked company's actual prefix explicitly (`applyCompanyPrefix(to, peekedCompany.issuePrefix)`) instead of trusting the ambient wrapper. Regression test added: `ui/src/components/SidebarNavItem.test.tsx` (new file), asserting the exact wrong-company scenario now navigates correctly.
